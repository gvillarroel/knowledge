## Executive conclusion

There is no accepted end-to-end lower-token Classical consultation version yet.

Several candidates reduced tokens dramatically on development tasks. The strongest current direct low-token result is exact V34 in V26: it used 79,744 native tokens instead of 6,015,810 for frozen canonical Classical, a 98.674426% reduction, and passed all reported numeric verifier metrics. It was still rejected because an independent paired semantic review found regressions in four of six cases. Validation and holdout therefore remained sealed.

V28 resolved the uncertainty around conservative ancestors. Exact V20, exact V21, and preferred-margin v2 each saved more than 97.8% against the same 6,015,810-token canonical control and completed without errors or observed retries. All three nevertheless regressed paired numeric metrics and independently reviewed semantics, so V28 selected no winner.

## Scope and acceptance contract

- This ledger measures the consultation step. Knowledge-folder construction is a different process and is outside the consultation lineage summarized here.
- The primary cost is native agent input tokens plus native agent output tokens.
- Cache-read tokens are informational and are not counted a second time.
- The current target requires more than 30% lower mean native tokens, median nonincrease, complete zero-retry and zero-error execution, no paired numeric verifier regression, and no independently reviewed semantic regression.
- Development is optimizer-visible. A development pass alone is not end-to-end acceptance.
- Validation is a one-way gate for one frozen winner. Holdout is a third sealed final gate.
- Historical versions used different cohorts, candidate budgets, and metric inventories. Their percentages are valid within their frozen comparisons but must not be ranked as one common leaderboard.
- Offline character or byte reductions are not token results.

### Evidence-class and inventory audit

This report uses three evidence classes. **Measured provider tokens** are native provider-reported input plus output tokens from an actual model call; a measured count may still describe a failed protocol and is useful-answer evidence only when the run produced a valid answer. **No-provider checks** include static validation, mock-provider simulations, local PREPARE/FINALIZE rehearsals, runtime-source inspection, and exact-harness work; they can establish implementation properties but cannot establish token savings or answer quality. **Local projections** are serialized characters, UTF-8 bytes, or payload ceilings; they are not model-token measurements.

The completeness audit found no missing named historical attempt. The frozen V66 source contains 79 unique attempt labels, and this report contains the same 79: the three pre-lineage compact-navigation attempts, V1-V62, both V63 revisions, five V64 revisions, six V65 revisions, and V66. The V29 table separately contains every revision R1-R13 exactly once. Rows whose negative disposition had previously been implicit were normalized below to say `Rejected`, `Did not advance`, or the applicable failed gate explicitly.

The final V29 organizer-controlled lineage is append-only stopped at sequence 121 and head `0bfe328449abac341e12b2304be9e3d7b602fea2d85d44ee553f2d3b37c2ff92`, with 100 registered evidence records.
