# EnterpriseRAG verifier conformance methodology

The native job completed **4/4** original trials: **4 passed**, **0 verifier failures**, and **0 execution errors**. Complete positive construction gates have documented passes in **4/4** cells. **24/24 attempted semantic negatives** were rejected for their predeclared reason. There were 24 intended negatives.

The [completed native report](../evaluations/reports/datasets/enterprise-verifier-conformance-001/README.md) records the outcome. The prospective contract below was frozen before execution.

This ordinary public engineering evaluation tests a corrected verifier on newly
authored fictional inputs. It neither evolves a knowledge skill nor supplies a
retrieval score, answer-quality score, scaling claim, independent validation,
promotion, or replacement for any previous EnterpriseRAG result. The completed
construction profiling study and its four failed native rewards remain immutable.

The motivating defect is public: the earlier record gate required every logical
record path to be a physical file even when `source-packed-v1` groups structured
records by source. The successor explicitly checks logical identity, trusted
source multiplicity, full physical bodies, and unique packed anchors, then runs
the unchanged family validator. The fixed adapter admits structured JSON only.

There is one `development` dataset, one authored conformance family, and four
related tasks, ordered Entity Graph single, Ensemble single, Entity Graph mixed,
and Ensemble mixed. Both variants cover the same nine application kinds. Single
has nine records, one per source; mixed has eighteen records, with source counts
1, 2, 3 repeated in sorted application order. Their generator, runtime, template,
oracle lineage, and motivating defect are shared. The single records are not
retained verbatim in mixed: titles and some record identifiers overlap, while
bodies and source/ontology IRIs explicitly distinguish variants. These fixtures
are visible development material and cannot later become independent validation.

The one-family inventory has capability `source-packed-verifier-conformance`,
domain `structured-enterprise-documents`, difficulty `contract-conformance`, and
resourceClass `cpu-two-threads`. Every task has responseMode `multi-file-artifact`.
Minimum realized coverage is exactly one family, four tasks, two producers, both
source-multiplicity variants, nine application kinds, one hardware stratum, and
one response mode. No population generalization, significance or rank is claimed.

The inputs have exactly five string fields: body, id, title, upstream_path and
upstream_sha256. The complete authored bodies include multiline, Unicode, NFD,
HTML-sensitive text, and punctuation. IDs may repeat across sources and must be
unique within each source after NFC normalization. Fresh output-root replay with
reversed source and record enumeration must reproduce every input byte.

Use the unchanged complete reference skill and deterministic native construction
agent. Each task performs two complete builds and two additional agent validators.
The exact existing derived image, runtime, plans, hashing provider (revision 1,
384 dimensions, normalized), model-cache tree and native Harbor 0.18.0 sources
must be prospectively bound. This measures deterministic tools, with zero LLM
calls; it does not measure Luna. Forced complete skill loading remains unchanged.

The fixed budget is four original native trials, one attempt, zero retries and
concurrency two. There are eight planned constructions and eight planned
additional agent-validation invocations. Agent native/useful/child deadlines are
1800/1750/1780 seconds. Agent and separate verifier each receive two CPUs and
6 GiB RAM; agent storage remains 24 GiB. Effective network is none, root is
read-only, mounted inputs and binding are read-only, and the agent cannot read
trusted verifier feedback. Preserve both native artifact routes and the exact
container/anonymous-volume cleanup observer.

Within each native 600-second verifier limit, one absolute 570-second useful
deadline covers the positive evaluator, all copying/mutation/hashing, negatives,
and outputs. At most seven complete evaluator calls occur per task, 28 in total.
The cap on trusted family-validator child invocations is two per task/eight total;
the entry guard narrows actual permitted calls to the positive invocation. Any
negative entry into trusted validation is a conformance failure, never a passing
negative, and never grants another opportunity.

After a successful complete positive evaluation, clone its pristine artifacts
independently six times. Mutate both knowledge and rebuild identically, refresh
only the agent-asserted knowledge file inventory and byte total, and preserve
all other artifacts, trusted sources, plans, binding, skills and phase/sample
streams. Independently reviewed source-bound targets specify the selected row,
canonical logical/physical paths, complete body and anchors. Single uses the first
sorted source; mixed uses the first sorted packed source; then select the first
canonical logical record path. The finite cases and exact expected rejections are:

| Case | Exact intended change | Required rejection |
| --- | --- | --- |
| Omitted record | Remove one authoritative ledger row | Knowledge omitted input records |
| Altered row body | Append a declared corruption to one row body | Actual knowledge record/body/source differs from bound input |
| Wrong logical path | Change row concept identity and copy a decoy document to that path | Logical concept identity differs from bound record |
| Missing physical document | Remove the required document from each copied tree | Missing actual concept document |
| Missing anchor or body | Remove one packed anchor; for single remove the complete physical body | Packed record anchors differ; single: Physical concept body differs |
| Unrelated physical body | Replace the required document body, preserving frontmatter and packed anchors | Physical concept body differs |

Every attempted mutant retains a digest/effect receipt and fresh evaluator logs.
Only the exact predeclared semantic ValueError before trusted validation counts
as a correct rejection. Unexpected acceptance, a different rejection, schema
exception, trusted-validator entry, timeout, infrastructure failure, or incomplete
evidence stops that task. Remaining checks stay unattempted. Public diagnostics
use fixed reason codes. A positive failure or interruption also leaves all
negatives unattempted.

The sole primary native reward is `verifier_conformance`, one if and only if the
complete positive and all six semantic negatives pass. Preserve the complete
positive observation and actual trusted-validator journal separately even if a
later negative fails. All four native rows, intended/attempted/passed counts,
execution errors and first stopping reason must remain visible. Construction
observations refer only to these fictional fixtures and cannot fill prior gaps.
